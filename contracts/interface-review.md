## 总评

9 字节协议总体**对齐得相当干净**，多数"妥协"是 **9 字节定长帧的固有约束**，不是迁就某端实现，不必改：

- ✅ **坐标单位 1 整数 = 5cm，与建图网格 1:1**——心跳 x/y 可直接当格索引，零换算误差。难得的优雅对齐，**保持**。
- ✅ **命令码对齐 ASCII**（`102='f'` …）——byte0 既是 App 状态也是命令码，自洽好记，**保持**。
- ✅ **大端 / 端口 5001 / 3s 急停**两端逐字节一致（证据见 `udp-protocol-crosscheck.md`）。

下面分类列"是否妥协 / 要不要一起改"。**真正建议两边一起改的只有 §2（cmd105 IP 打包）。**

## 1. byte 字段按命令复用（结论：固有约束，**接受**，仅需契约写清）

`byte1` 随命令是 `runState`(1) / 房间号(104) / `robot_id`(108) / IP段(105)；`byte[3-6]` 是 `endX/endY` 或 IP 低字节或矩形角点。
- **判定**：9 字节定长帧塞多语义的**必然结果**，非迁就 A。App `encodeSend` 已按命令构造、`udp-protocol.md` 有逐命令字段表，可读性够。
- **建议**：不改协议；只需让 `udp-protocol.md` 的"每命令 byte 含义表"保持最新（现已是）。

## 2. cmd105 主机 IP 打包进**散列字节 [1,2,4,6]**（结论：**真不优雅** → Q10，非阻塞）

cmd105('i') 把主机 IP 四段塞进 `byte[1],[2],[4],[6]`——**跳过 [3],[5]**。根因：复用了 `endX/endY` 两个**大端 int16** 字段，
单字节的 IP[2]/IP[3] 落在它们的**低字节**（[4]/[6]），高字节 [3]/[5] 恒为 0 空着。
- **判定**：**为复用既有 int16 字段做的不优雅折中**——散列字节难读易错（编解码两端都要记住"跳 [3][5]"）。
- **建议（→ Q10）**：cmd105 不复用 int16 字段，IP 四段放**连续** `byte[1..4]`（[5][6] 留 0）。两端各改一行解析。
  **非阻塞**：现状能工作；A 哪天动 cmd105 解析时顺手改即可，新写的车载 agent 触发 cmd105 时按最终布局实现。

## 3. cmd107/108 两帧暂存式矩形（结论：固有约束，**接受**；distributed 走 agent 更稳）

子区域 = `cmd107`(对角点1，紫派暂存) + `cmd108`(对角点2 + `robot_id`，触发规划)。一个矩形拆成**两帧 + 紫派侧隐式状态**。
- **判定**：9 字节装不下 `(cmd + robot_id + 两点)=10 字节`，故**必须两帧**——是**帧长固有约束**，非迁就 A。
- **风险**：两帧在 **WiFi 直连**下若丢包/乱序，矩形会错配（corner1 残留上一次）。
- **建议（无需 A 改协议）**：① **distributed 模式优先走 agent/黑板**——矩形在黑板上原子下发，agent 在**本机 localhost**（可靠）发 107/108，
  两帧脆性消失（`car-agent-plan.md` §6.3 已是此路径）。② 若保留**平板直连划区**（无 agent 单车），它本就是"兜底"路径，
  脆性可接受；真要加固再议（给 107 加回执/序号），**低优先**，等 agent 路径验证后定。

## 4. 地图相关

### 4a. 地图首行 7 字段（结论：按固定位置取 `parts[2]/[3]`）
A 的 HTTP 地图文件首行 = `range resolution height width metersPerPixel x0 y0`（7 值，`Navi/map/MapServer.cpp` 写出）。`height/width` 固定在第 3、4 字段；末两个字段是 `x0/y0` 世界偏移，不能当高宽。
- **判定**：旧的“取末两个整数作为高宽”只适用于 4 值分片头语境，不适用于 App 拉取的 HTTP `defultMap.txt`。A 侧说明已在 2026-06-12 订正。
- **App 侧要求**：主路径按固定位置 `[2]=height,[3]=width` 解析，同时解析 `metersPerPixel/x0/y0` 供坐标换算；旧 fixture 兼容逻辑可作为防御保留。

### 4b. 地图就绪靠"字节数 ≥ 324e4"（结论：脆，**已在 Q8**，并入跟踪不另立）
`MAP_READY_MIN_BYTES = 324e4` ≈ 预期 1800×1800 满图字节数（`constants/ui.ets`）。真图更小则**永远判不就绪**。
- **判定**：典型"无就绪信号"下的脆启发式。**已立 Q8**（请 A 在存图完成给明确信号取代大小阈值）+ App 短期已用
  "`cmd2 结束建图`后主动拉一次图"绕开（见 `docs/archive/feature-parity-review.md`）。R1 **不另开问题**。
