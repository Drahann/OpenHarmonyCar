## 内容摘要（Executive Summary）

本项目是一台**面向工业场景的自主巡检机器人**，由三名成员从硬件接线、电机轮控、激光 SLAM、A\* 导航、全覆盖路径规划、昇腾视觉模型（自采集数据、自标注、自训练），到鸿蒙平板控制 App、车载分布式协同 agent，**全栈自主搭建、不依赖任何 ROS 中间件**。

系统由**三个异构节点**组成，运行在三种不同的硬件与操作系统之上，通过**四条经过逐字节对账的契约化链路**协同工作：

| 节点 | 硬件 / 系统 | 语言 | 职责 |
|---|---|---|---|
| **平板控制端** | HarmonyOS 平板 | ArkTS | 总控 / 规划 / 可视化：建图、选点、路径下发、多机调度、仪表监看 |
| **紫派主控（每台车）** | Purple Pi OH（RK3566 / OpenHarmony 5.0） | C / C++ / Python3 | 激光 SLAM 建图与定位、A\*/D\* 导航、全覆盖路径、差速轮控、UDP↔LCM 桥 |
| **香橙派视觉** | OrangePi AI Pro（昇腾 310B NPU） | Python / C++ | 工业仪表实时检测、关键点读数、DeepSeek 报告生成 |

核心能力闭环：**激光自主建图 → A\* 单点导航 → 全覆盖遍历清扫 → 多机协同分区 → 边缘视觉读表 → 异常告警与智能分析报告**。整套系统**国产化、自主可控、无"卡脖子"依赖**：操作系统是开源鸿蒙、AI 算力是华为昇腾、上层语言是国产 ArkTS、导航与覆盖算法全部成员独立实现，连仪表识别模型的数据集都是自己采集标注训练的。

## 第一章　项目背景与立项价值

> 本章为概述，完整的政策依据、行业报告数据、竞品逐项对比与可核查来源见配套文档 [`04-优势对比与行业背景.md`](04-优势对比与行业背景.md)。

### 1.1 行业背景：工业巡检正从"人工"走向"自主"

工业巡检是电力、石化、轨道交通、冶金等流程工业**安全生产的第一道防线**。传统人工巡检长期面临三类结构性痛点：

1. **高危环境威胁人身安全**——变电站的高压电场、化工焦炉车间的高温高粉尘强腐蚀气体、辐射区与有毒气体环境，使巡检人员长期暴露于风险之中。
2. **效率低、覆盖不全、数据离散**——大型流程工业设备数以万计，人工巡检工作量剧增、存在检测盲区，纸质或离散记录难以形成可追溯的数据资产。
3. **读数主观、易漏判**——大量现场仍是**指针式机械仪表**，人工读数主观、疲劳易错，夜间与高位仪表尤甚。

行业研究显示，智能巡检机器人在变电站场景已能以**视觉算法识别仪表读数、刀闸状态，准确率达 99%、效率是人工的 5 倍**；石化厂区的巡检机器人效率是人工的 4 倍，通过最优路径与多机协同，可将巡检频次从"每日 2 次"提升到"每小时 1 次"，**人力成本下降约 60%**。这正是本项目要解决的真实问题。

### 1.2 市场与政策：双重风口

- **市场高速增长**：2025 年中国智能巡检机器人市场规模约 **27.48 亿元**，预计 2026 年达 **31.85 亿元**，年增速约 **15.9%**；其中**电力领域占比高达 88.54%**，是最大应用市场。
- **国家政策强力牵引**：
  - 工信部《人形机器人创新发展指导意见》将 **2025 定为关键节点**，2025 年被业界普遍称为"量产元年"（整机企业超 140 家、发布产品超 330 款）。
  - 国务院 2025 年 8 月印发《关于深入实施"人工智能+"行动的意见》，部署六大重点行动与**八项基础支撑能力**，其中明确"**促进开源生态繁荣**"与"**提升安全能力水平**"——本项目所选的开源鸿蒙 + 昇腾国产路线，正是政策的精准落点。
  - 2025 年 12 月，工信部"人形机器人与具身智能标准化技术委员会"成立，具身智能进入标准化与产业化加速期。
- **信创与自主可控**：在"卡脖子"突破的国家战略下，央企信息系统加速国产化替代。机器人作为**软硬件深度耦合的系统工程**，其操作系统、AI 算力、开发语言、核心算法的自主可控具有典型示范意义。

### 1.3 立项价值与目标场景

本项目的差异化定位是：**用一套完全国产、自主可控的技术栈，做出一台可建图、可导航、可全覆盖、可多机协同、可读表告警的工业巡检机器人**，并把"复杂的机器人系统"收敛到一块**平板上像用地图 App 一样简单的交互**里。

**目标应用场景**：变电站 / 配电室设备巡检、化工与石化厂区危险区域巡检、仓储与厂房地面全覆盖巡查、轨道交通隧道与机房巡检、以及任何"环境危险 + 仪表密集 + 需要可追溯数据"的工业现场。

## 第二章　系统总体设计

> 架构图、时序图、数据流图见配套文档 [`03-原理与流程图.md`](03-原理与流程图.md)。

### 2.1 总体架构：三节点 + 四链路

系统刻意采用**异构分布式架构**，每个节点只做自己最擅长的事，节点之间用**契约化接口**解耦：

```
        ┌─────────────────────────┐
        │   平板控制端 (HarmonyOS)  │  总控 / 规划 / 可视化
        │      ArkTS App           │
        └──────────┬───────┬───────┘
   UDP 9字节:5001  │       │  WebSocket /ws/video
   HTTP 拉图:8000  │       │  (JPEG帧 + 读数JSON)
   软总线黑板      │       │
        ┌──────────┴───┐   └──────────────┐
        │ 紫派主控(每车) │                  │
        │ RK3566/OH5.0  │            ┌─────┴──────┐
        │ SLAM/A*/覆盖  │            │ 香橙派视觉   │
        │ 轮控/UDP↔LCM │            │ 昇腾310B NPU │
        └───────────────┘            └────────────┘
```

**四条链路职责分明、互不打扰**：

| 链路 | 协议 | 端口 | 承载 |
|---|---|---|---|
| 控制 / 心跳 | 自定义 **9 字节二进制 UDP**（大端） | 5001 | 命令下发 + 500ms 位姿心跳 |
| 地图传输 | HTTP（紫派 `python -m http.server`） | 8000 | 压缩图 `zipedMap.txt` / 普通图 `defultMap.txt` |
| 多机协同 | 鸿蒙**分布式软总线** `distributedDataObject` | — | `FleetMission` 任务黑板（协调态） |
| 视觉流 | **WebSocket** + REST | 8000(香橙派) | JPEG 帧 + 读数/告警 JSON + 配置/报告 |

**关键设计原则——视觉链路与导航链路彻底解耦**：视觉的 WebSocket 自持一条连接，不与导航的 UDP/HTTP 共享任何 socket；进出视觉视图只连/断本 WS，导航的保活、控制、建图照常运行。两条链路在网络层、线程层、代码依赖层三重隔离，互不阻塞。

### 2.2 模块功能介绍

#### 2.2.1 激光感知模块（紫派）
双雷达配置：**LDS-50C-2**（建图）+ **RPLIDAR A2M8**（导航），通过 cp210x 串口驱动接入。激光点云经 `HOKUYO_LIDAR` LCM 信道送入导航模块，供 SLAM 建图与实时定位。

#### 2.2.2 导航与定位模块（紫派 Navi）
基于多分辨率扫描匹配（Multi-Resolution Scan Matcher）+ 高斯估计 + 粒子滤波（KLD 采样）的 SLAM，实时输出 `CURRENTPOSE`；A\* / D\* 全局规划 + 局部跟踪，输出 `PATH`（速度 / 角速度）。**全部自研，不使用 ROS 的 move_base / amcl / gmapping**。

#### 2.2.3 LCM 通信模块（紫派内部）
基于 UDP 组播的轻量消息总线，串起雷达、轮控、导航三大模块。信道包括 `HOKUYO_LIDAR / POSE / ROBOT_CONTROL / CURRENTPOSE / PATH / wheel_ctrl`，命令号体系（7 初参 / 10 加载图 / 20 加目标点 / 30 建图 / 32 存图 / 122-127 覆盖与全路径）见附录。

#### 2.2.4 路径规划模块（紫派）
- **单点导航**：A\*（栅格代价：空旷 / 近障碍 / 危险分级），融合激光地图 + 视觉墙信息。
- **全覆盖**：优先**BCD（Boustrophedon 单元分解）**生成牛耕往复路径，失败回退**矩形 zigzag 牛耕**；另支持**最小生成树**算法。覆盖路径落地为 `roadFile.txt`（每行一个 `x,y` 栅格点）。
- **多机协同覆盖**：平板划对角矩形子区域，各车按 robot_id 分段执行；车间用独立的 `COOP_AVOID` 多播 LCM 通道做协同避障。

#### 2.2.5 系统控制模块（紫派 udp2lcm 桥）
UDP↔LCM 双向翻译器：把平板的 9 字节命令解析成 LCM 命令发给算法 / 轮控模块；把位姿等回包封装成 9 字节心跳回传平板。内置 **500ms 心跳** + **3s 看门狗急停**（3 秒未收到任何指令立即停轮，防失控）。

#### 2.2.6 差速轮控模块（紫派 serial）
订阅 `PATH` / `wheel_ctrl` LCM，把速度 / 角速度解算成左右轮差速，经串口下发驱动板；每 15ms 经 `POSE` 反馈估算坐标，形成里程闭环。

#### 2.2.7 人机交互模块（平板 App）
Google-Maps 范式的全屏地图控制台：四态设备发现连接、SLAM 建图引导、栅格选点、A\* 导航、全覆盖、多机协同、仪表视频 PiP 与全屏识别、设备互信配对、手填 IP 兜底。详见第五章。

#### 2.2.8 仪表识别模块（香橙派）
昇腾 NPU 上的两级流水线：**YOLOv5s 仪表检测 → 裁剪 ROI → Simple Baselines 4 关键点 → 几何换算读数**；端到端 ~34ms、~29FPS。叠加 DeepSeek-R1 蒸馏模型做趋势 / 异常分析报告。

### 2.3 设计思路与权衡

- **为什么异构三节点而非单机**：建图导航需要实时性强的 C/C++ + 激光，视觉推理需要 NPU 算力，交互可视化需要现代 UI 框架——把它们放到各自最合适的硬件上，再用契约解耦，是工程上最稳健的选择。
- **为什么自定义 9 字节 UDP 而非 ROS topic / gRPC**：嵌入式实时控制要求极低开销与确定性；9 字节定长二进制 + 大端，单包即一条完整指令，零序列化框架依赖，紫派 C 侧 `htons/ntohs` 直接解，平板 ArkTS `DataView` 直接读。
- **为什么用鸿蒙分布式软总线做多机协同**：软总线提供**设备发现 + 可信组网 + 数据对象自动同步**，让"多车共享一块任务黑板"成为系统原生能力，而非自己造一套 RPC。
- **为什么 byte0 同时是 App 状态与命令码**：取值刻意对齐 ASCII（如 `fullpath_startRoute=102='f'`、`forceCreateMap=0x6d='m'`），一个字节同时表达"App 当前在哪个状态"和"要紫派做什么"，极简且自解释。

## 第三章　关键技术原理

> 本章讲"怎么做到的"，公式 / 状态机 / 时序图见 [`03-原理与流程图.md`](03-原理与流程图.md)。

### 3.1 激光 SLAM 建图与定位

紫派 `Navi` 模块的 SLAM 是**全自研**的扫描匹配 + 概率栅格方案：

- **概率栅格地图**（`MapServer::saveProbMap`）：以 **0.05m/格** 分辨率维护占据概率，落盘为 `defultMap.txt`，首行 7 值 `range resolution height width metersPerPixel x0 y0`，数据区空格分隔（`-1`=障碍 / `0`=空旷 / `2`=已覆盖）。`x0/y0` 是栅格最小角的世界坐标（米，可负），世界↔栅格换算：`grid = (world − x0) / metersPerPixel`。
- **多分辨率扫描匹配**（`MultiResolutionScanMatcher`）：由粗到细搜索激光帧与已建地图的最佳位姿对齐，兼顾速度与精度。
- **粒子滤波 / KLD 采样**（`particlefilter/KLD`）：自适应粒子数维护位姿分布，抑制累计漂移。
- **强制重建语义**：紫派 `cmd0` 在已有图 / 导航态时"只当心跳、忽略建图"，因此 App"开始建图"下发 **`'m'`/0x6d**（`forceNewMap=true`）才会清空旧图从头建——这是经真机定位的关键接口语义，已写入契约。

### 3.2 A\* / D\* 路径规划

A\* 规划器（`CAstar`，`Navi/planner/Astarplanner`）特性：

- 栅格状态分级：`FreeSpace / Occupied / Near_Obstacle`，并赋不同代价（`heighcost / neardanger / danger`），让路径**主动远离障碍**而非贴墙。
- 支持 **A\* / D\* / BFS** 三种搜索；D\* 支持动态重规划（覆盖探测时反复用）。
- **视觉墙融合**：把视觉识别到的障碍作为额外代价注入 `visionMap`，与激光地图联合规划。
- 到达判定（App 侧镜像）：位姿与目标的栅格距离平方 ≤ 32 cell²（≈ 28cm）即判定到达。

### 3.3 全覆盖路径规划（重点）

这是本项目的算法亮点之一，**两套算法 + 优雅降级**：

1. **首选 BCD（Boustrophedon Cellular Decomposition，牛耕单元分解）**：`bcdCoverage.buildPathFromGridState` 把框选矩形按障碍切成若干无障碍子单元，在每个单元内做牛耕往复（来回扫描线），单元间用 A\* 连接，生成连续覆盖路径。
2. **回退矩形 zigzag 牛耕**：BCD 失败时，按矩形长边方向（`xlen`/`ylen` 谁长以谁为主轴）做规则的往复扫描；刷宽由机器人安全半径 `safesize` 决定。
3. **最小生成树（MST）覆盖**：作为可选算法（单车全路径），App 提供"牛耕 / 最小生成树"算法选择。
4. **自动 / 手动房间边界**：覆盖区域既可由凸包算法自动圈定，也可由操作员在平板手动选点框定。

覆盖路径写入 `roadFile.txt`；覆盖过程中 App 端按位姿足迹**实时累计已覆盖面积与进度**（详见 5.4）。

### 3.4 差速轮控与里程闭环

轮控订阅 `PATH`（导航输出的 v/ω）或 `wheel_ctrl`（建图期遥控），用差速模型 `v_left/v_right = v ∓ ω·d/2` 解算左右轮速，经串口下发驱动板；每 15ms 由编码器反馈经 `POSE` 回传位姿估计，与 SLAM 定位互补。**坐标单位统一**：1 整数单位 = 1/20m = 5cm，与地图格子 1:1；朝向 `r` 用度，范围 [-180,180]，0° 指向 +X、正角 CCW 朝 +Y。

### 3.5 UDP 9 字节协议与 LCM 桥

**发送方向（App→紫派，9 字节）**：byte0=命令码，byte1=运动方向 / 房间号 / robot_id（按命令复用），byte2=速度，byte3-4=目标 X（int16 大端），byte5-6=目标 Y，byte7-8=保留。
**接收方向（紫派→App 心跳）**：byte0=状态（3=带坐标），byte3-4/5-6/7-8=当前 x/y/r。
`udp2lcm` 桥把命令翻译成 LCM：`startRoute(3)→加目标点(20)`、`forceCreateMap('m')→建图(30,forceNewMap)`、`afterEnd(2)→存图(32)+加载(10)`、`distAreaCorner1/2(107/108)→覆盖(122)+跟踪(123)` 等。完整命令表见附录。

### 3.6 边缘视觉推理流水线

香橙派昇腾 NPU 上（模型经 ATC 转 `.om` 原生推理，ACL 上下文独立子线程 + 帧队列 + 跳帧保实时）：

```
USB摄像头 → 抓帧 → YOLOv5s仪表检测(21ms) → 裁剪ROI
  → Simple Baselines关键点(8ms, 输出4点热力图) → 亚像素精炼
  → 几何换算读数 → 渲染叠加 → JPEG编码(q=50) → WebSocket推送
```

**读数几何**：以表盘圆心为原点，取指针相对"零刻度→满刻度"的**顺时针夹角占比**乘满量程：
`reading = CW(zero→pointer) / CW(zero→full) × 满量程`（占比 clamp 到 [0,1]）。4 关键点 = `center / pointer_tip / zero_mark / full_mark`。**多表支持**：YOLO 置信度阈值降到 0.10 + 长宽比(0.6–1.7) + 面积(<85%全图) 过滤误检框，一图多表各自读数。

### 3.7 多机协同：软总线黑板模型

摒弃旧的"`startAbility` 当 RPC + `Want` 塞一次性快照"的别扭机制，改为**共享黑板、反应式读写**：所有节点常驻加入同一 `distributedDataObject` 会话，共享一块 `FleetMission` 任务黑板（phase / area / assignments / robots / 进度）。谁改谁广播，其余端 `onChange` 响应。平板做规划（划分子区域、监看），车载 agent 把黑板里属于自己的任务翻成本机 UDP 下发、把位姿进度写回黑板。子机入场用 `cmd5` 加载图归零到 master 起点 (0,0,0)，实现"从同一物理起点出发→坐标系按构造对齐"，无需全局重定位。

## 第四章　软件实现

### 4.1 应用层：鸿蒙平板 App（ArkTS）

采用 ArkTS + ArkUI 声明式开发，关键工程化实践：

- **协议编解码**（`model/protocol.ets`）：`encodeSend` 把命令编为 9 字节大端缓冲；`encodePullMap` 单独处理 cmd105 的"主机 IP 四段打进 byte[1,2,4,6]"特殊布局；`decodeReceive` 解心跳。与紫派 `udp2lcm.c` **逐字段对账**。
- **地图服务**（`MapService.ets`）：`fetchMapPreferZiped` 优先拉压缩图、失败回退普通图；`parseMap` 统一两种源格式（空格 `-1/0` / 密排 `1/0` / 压缩 `ZMAP1`）归一为栅格，做包围盒裁剪 + 正方形化；**`decodeZipedRow` 用 BigInt 解 64 位字**（ArkTS number 仅 53 位精度，必须 BigInt 否则丢高位）。
- **传输层**（`RobotTransport.ets`）：UDP 收发、设备发现（广播 `0x06`）、保活节流。
- **多机服务**（`FleetMissionService.ets`）：软总线发现 + 入会话 + 黑板读写，传输层无关（可在软总线受阻时切 LAN socket）。
- **视觉服务**（`VisionService.ets`）：自持 WebSocket，引用计数管理（PiP + 全屏共享一条连接），退避重连，**整段 try/catch 容错**（视觉字段缺失也不崩，读数显"—"）。

### 4.2 车载轻 agent（ArkTS，常驻紫派）

`car-agent/` 是常驻紫派的**无界面 ArkTS 节点**（code-complete）：入会软总线持黑板，`Reconciler` 把黑板任务翻成本机 9 字节 UDP（localhost）幂等下发，把心跳位姿节流写回黑板。bundleName 与平板同为 `com.example.carapp`（软总线黑板同步硬前提）。与平板 App 共享 UI 无关层（model/constants/utils/service）。

> 工程现状：本项目同时实现并保留了**两套多机方案**——"软总线 DDO + 车载 agent"（创新点、产品级目标）与"平板直连双车 UDP"（方案A，应对硬件 AP 隔离的稳健退路，当前默认）。两者并存、可一键切换，传输层接口设计为传输无关。

### 4.3 中间层：紫派主控（C/C++/Python3）

- **udp2lcm 桥**：`udp.c` 绑定 `INADDR_ANY:5001`，首包捕获客户端并启心跳线程；发现 ping(`0x06`) 只回包、不记客户端、不武装急停；3s 看门狗发 `wheel_ctrl{0,0}` 急停。`udp2lcm.c::parseCmd` 做命令翻译。
- **Navi 导航**：SLAM、A\*/D\*、全覆盖（`CoverageThreadProc` + `CreateFullPath`）、协同避障、地图落盘与 HTTP 暴露。
- **轮控**：`serial.c` 差速解算 + 串口驱动。
- **地图服务**：`chdir(/data/test)` 后 `python -m http.server :8000` 暴露地图文件。

### 4.4 视觉层：香橙派（Python / 昇腾）

- **FastAPI + Uvicorn** 服务（`web/backend/main.py`）：`/ws/video` 推 JPEG+JSON，REST 提供 `/api/summary`（实时状态）、`/api/history`（历史）、`/api/thresholds`（告警阈值）、`/api/gauge/configs`（量程标定）、`/api/data/report`（DeepSeek 报告）等完整接口。
- **推理**（`deployment_bundle/`）：YOLOv5s（AIPP OM）+ Simple Baselines（备 RTMPose）OM 原生推理。
- **DeepSeek-R1-Distill-Qwen-1.5B**（`deepseek_service.py`）：本地化大模型，基于最近 24h 读数生成趋势/异常分析报告，SSE 流式返回；生成时暂停摄像头释放 NPU。
- **设备发现**（`discovery_responder.py`）：监听 5001，收到 App 的 `0x06` 广播回 `0x07`，让动态 IP 的香橙派可被平板自动发现。

## 第五章　人机交互与产品体验

App 把"复杂机器人系统"收敛为**像用地图导航 App 一样简单**的体验：全屏地图打底，浮层操控，分步引导，每一步都有清晰反馈。

### 5.1 设备发现与四态连接

局域网广播发现（`0x06`），按回包**源 IP** 自动收集在线设备，**免手填 IP**；香橙派视觉设备以 `0x07` 区分、自动设为视觉源。单台车连接状态机：**⚪已发现 → 🟡连接中 → 🟢已连接·心跳正常 → 🔴丢失**，每 600ms 由心跳新鲜度刷新，驱动命令门控（未连不可下发）。提供**设备互信配对**（软总线多机前置）与**手填 IP 兜底**（公共 AP / 客户端隔离场景）。

### 5.2 SLAM 建图引导

底部建图卡引导"开始建图 → 摇杆探索 → 结束建图"。开始建图发 `'m'` 强制重建；摇杆 + 速度滑块遥控车体探索，墙体随激光扫描在地图上**实时生长**；结束建图存图落盘并自动拉图（优先压缩图 `ZMAP1`，~6× 更小，解决"6.5MB 普通图在单线程 server 上拉不完"）。

### 5.3 选点交互：先选后发，可中途重选（本次新增）

> **设计动机**：旧逻辑是"点【开始选点】→ 点地图 → 立即下发"，一点就发，无法中途反悔或微调。

改进为**两段式武装选点**：

1. 点【**开始选点**】进入武装态（自动收起底卡、地图最大化便于点选）；
2. 在地图上选点期间**只暂存、不下发**（astar 1 个目标点 / fullpath 4 个顶点 / distributed 2 个对角点），可任意重选微调，未提交前**绝不污染紫派状态**（不发 cmd104/107/108）；
3. 点【**结束选点**】才把本轮暂存的选点**统一下发**；或点【**取消**】放弃本轮。

这一改动**纯属 App 侧"下发时机"**——9 字节协议的命令字节与语义、建图的 `'m'`/0x6d 强制重建全部不变，与紫派完全兼容。底部控制栏新增"取消 / 结束选点"按钮对，顶部 Peek 行也给出"最该点的那一个"主操作。

### 5.4 覆盖进度上图：与地图同屏一眼可见（本次新增）

> **设计动机**：覆盖进度原先埋在底部控制栏里，边覆盖边看不方便；分布式多车进度更挤。

把【全路径覆盖】与【多机协同】两种模式的**"覆盖进度"从控制栏摘出**，做成浮于地图右上角的 **CoverageHud** 卡片，与地图同屏、边扫边看：

- **单车全路径**：进度条 + 百分比 + "已覆盖 ≈ X m²"（按覆盖足迹格数 × 单格面积 0.0025m² 实时累计）。
- **多机协同**：每车一行（车号 + 进度条 + 百分比·面积）。

HUD 仅在"已开始覆盖 / 已划区域"时显示（避免空卡），定位在右上角，**不与缩放 FAB、底部卡、PiP 小窗重叠**。同时地图上绘制各车**行走轨迹**（彗尾观感：软辉光底 + 历史淡痕 + 头部渐亮）与**覆盖足迹**填充。

### 5.5 视觉识别：边导航边瞥表

控制页左上角 **PiP 小窗**可随时展开瞥仪表（独立 WS，不打扰导航），可放大进**全屏 VisionPage**：视频区显示检测框 + 4 关键点 + 读数，下半部读数面板（表 1/表 2 值 + 单位 + 状态、fps / 推理 ms / 检测数），告警表变红；底部可一键生成 DeepSeek 分析报告。

### 5.6 视觉设计语言

暖米白纸底 + 墨绿品牌色（`#485c11`）+ 钢蓝链路 + 砖红告警的克制配色，全局禁深色底 / 禁霓虹辉光；数据 / 坐标 / IP 用等宽体；牛皮纸图纸地图打底、墙体平滑矢量等高线渲染。统一的 `theme.ets / motion.ets / icons.ets` 三个单一来源保证一致性。

## 第六章　演示与实测效果

### 6.1 完整能力闭环（实测跑通）

1. **发现连接**：同热点广播发现双车 + 香橙派，点击连接，四态机正常流转。
2. **自主建图**：`'m'` 强制重建 → 摇杆探索 → 墙体实时生长 → 结束存图 → 自动拉压缩图渲染。
3. **A\* 导航**：武装选点 → 落红色泪滴 pin → 开始导航 → 车沿 A\* 路径行驶、轨迹绘出 → 到点自动判定。
4. **全覆盖**：选牛耕 / 最小生成树 → 框选 4 顶点 → 自动启动牛耕往复 → 覆盖足迹绿色填充 + 面积 count-up。
5. **多机协同**：双车各划对角矩形子区域 → 分区清扫、互不重叠 → 各车进度条实时刷新；车间 `COOP_AVOID` 协同避障。
6. **仪表识别**：PiP 瞥表 → 全屏识别（检测框 + 关键点 + 读数）→ 告警变红 → DeepSeek 生成趋势报告。

## 第七章　特色与创新（概述）

> 穷举式创新清单（架构 / 协议 / 算法 / 交互 / 国产化等全维度）见 [`02-创新点穷举.md`](02-创新点穷举.md)。

**一句话**：本项目最大的特色是**"全栈国产自主可控 + 工程级契约化协作 + 把机器人做成像地图 App 一样好用"**。择要：

1. **全自研算法栈、零 ROS 依赖**：SLAM、A\*/D\*、BCD 全覆盖、差速轮控全部成员独立实现，不依赖 ROS 的任何导航 / 建图 / 通信组件。
2. **昇腾视觉模型从数据到部署全自主**：自采集数据集、自标注、自训练 YOLOv5s + Simple Baselines，ATC 转 OM 在昇腾 NPU 原生推理，连分析大模型（DeepSeek-R1 蒸馏）都本地化部署。
3. **国产化技术底座**：开源鸿蒙内核 + 鸿蒙分布式软总线 + 国产 ArkTS 语言 + 华为昇腾算力，全链路无"卡脖子"外部依赖。
4. **鸿蒙分布式软总线做多机协同**：以"共享任务黑板"取代远程拉起，多车协同是系统原生能力。
5. **视觉链路与导航链路三重解耦**：网络 / 线程 / 代码依赖隔离，互不打扰。
6. **9 字节极简协议 + 契约化协作**：byte0 对齐 ASCII 同时表达状态与命令；三端代码物理隔离、互不编译依赖，靠 `contracts/` 逐字节对账集成。
7. **压缩地图 ZMAP1**：1bit/格 + BigInt 解码，解决弱网慢传输。
8. **产品级交互**：四态连接、分步引导、两段式武装选点、覆盖进度上图、轨迹彗尾、PiP 瞥表。

## 第八章　技术规格与附录

### 8.1 UDP 命令码表（byte0，节选）

| byte0 | 命令 | 字符 | 紫派动作 |
|---|---|---|---|
| 0 | beforeStart | — | 心跳 / 兼容建图（有图时只当心跳） |
| 1 | pending | — | 遥控运动（byte1=方向, byte2=速度） |
| 2 | afterEnd | — | 结束建图：停轮 + 存图(32) + 加载(10) |
| 3 | startRoute | — | 设目标点 → 加目标点(20) |
| 4 | endRoute | — | 取消导航(23) |
| 5 | loadMap | — | 加载图 + 位姿归零(0,0,0) |
| 0x06 | discoveryPing | — | 发现 ping（只回包、不武装急停） |
| 102 | fullpathStartRoute | 'f' | 启动全路径(127)，byte1=算法 |
| 103 | fullpathStartover | 'g' | 取消全路径(126) |
| 104 | fullpathSelect | 'h' | 单机全路径选顶点(125) |
| 105 | distributed | 'i' | 子机拉主机图(124)，IP 在 byte[1,2,4,6] |
| 106 | distributedEnd | 'j' | 加载图(10) + 收主机目标点 |
| 107 | distAreaCorner1 | 'k' | 覆盖矩形对角点1（暂存） |
| 108 | distAreaCorner2 | 'l' | 对角点2 + robot_id → 覆盖(122)+跟踪(123) |
| 0x6d | forceCreateMap | 'm' | **强制重建图**（清旧图、从头建） |

### 8.2 LCM 命令号（ROBOT_CONTROL）

7 初参 / 10 加载图 / 20 加目标点 / 23 删目标点 / 30 建图 / 32 存图 / 122 矩形覆盖 / 123 分布式跟踪 / 124 拉主机图 / 125 全路径选顶点 / 126 取消全路径 / 127 启动全路径。

### 8.3 坐标系约定

1 单位 = 1/20m = 5cm（与格 1:1）；朝向 `r`=度 [-180,180]，0°=+X，正角 CCW 朝 +Y；原点 = 紫派建图初始位姿；世界↔栅格：`grid=(world−x0)/mpp`。

### 8.4 术语表

SLAM（同步定位与建图）｜A\*/D\*（启发式 / 动态全局路径搜索）｜BCD（牛耕单元分解全覆盖）｜LCM（轻量通信组播总线）｜NPU（神经网络处理器，昇腾）｜软总线（鸿蒙分布式设备互联）｜DDO（distributedDataObject 分布式数据对象）｜ZMAP1（自定义 1bit/格压缩地图格式）。
