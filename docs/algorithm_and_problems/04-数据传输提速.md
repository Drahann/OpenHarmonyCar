# 数据传输提速 —— 瓶颈定位与优化方案

> 目标：让"地图、覆盖路径、激光、位姿"等数据在 App↔车、车↔车之间传得更快。本文先**定位现有瓶颈**
> （含代码证据），再给**分层优化方案**与预期收益。代码不在本文范围。
>
> 依据：`origin/purplepi-control` 源码 + 根目录 `接口功能与对接问题说明.md`。

---

## 0. 现有数据通路总览

| 通路 | 载体 | 用途 | 现状速率瓶颈 |
|---|---|---|---|
| App ↔ 紫派 | UDP 5001，9 字节 | 控制命令 / 心跳 | 小包，无瓶颈 |
| 紫派 → App / 上层 | **LCM `MAPFILE`** | 地图分片上送 | 🔴 每行 sleep 50ms |
| 车 → 车 | **HTTP `python -m http.server`** | 拉地图 / roadFile | 🔴 单线程、无压缩、整文件 |
| 内部 | LCM `HOKUYO_LIDAR/POSE/PATH/...` | 雷达/位姿/轮控 | 🟡 laser 编码冗余 |

两条**大数据量**通路（地图）都有明显可优化点，下面重点谈。

---

## 1. 🔴 最大瓶颈：MAPFILE 每行人为 sleep 50ms

### 证据
`Navi/main.cpp` 地图上送循环（约 227–256 行）：
```c
while ((read = getline(&line, &len, fp)) != -1) {
    int bytenum = (int)read;
    usleep(50000);                 // ← 每读一行睡 50ms
    ...
    cmd.nbparams = bytenum;
    cmd.bparams = (unsigned char *)line;
    robot_control_t_publish(lcm, "MAPFILE", &cmd);   // 一行一条 LCM 消息
}
```
地图按**行**发，每行一条 LCM 消息，**每行强制 `usleep(50000)`**。

### 代价
- 0.05m 分辨率下，一张 20m×20m 的图约 **400 行** → 仅 sleep 就 **400 × 50ms = 20 秒**；
  30m×30m → ~600 行 → **30 秒**。地图越大越慢，且与内容无关，纯粹是节流等待。
- 这直接拖慢"建图完成 → App/子机拿到图 → 开始导航/覆盖"的整条链路，是体感最差的一段。

### 为什么会有这个 sleep
多半是**流控**：LCM 默认走 UDP 组播，接收端缓冲有限，连续猛发会丢包，于是用 sleep 限速。但 50ms/行过于保守。

### 优化（按收益排序）
1. **批量打包**：一条 LCM 消息发**多行**（如 16~32 行），sleep 总次数降一个数量级。
2. **压缩后再发**：地图高度可压缩（见 §3），先压缩整图再分片，字节数降 5~50 倍，分片数随之骤降。
3. **调小 sleep**：若仍需节流，按"每 N KB sleep 几 ms"而非"每行 50ms"，根据实测丢包率标定。
4. **大块走可靠传输**：批量地图改用 TCP（或 LCM 之上加确认/重传），从根上摆脱"靠 sleep 防丢包"。

> 预期：仅"批量 + 压缩 + 降 sleep"三项叠加，地图上送从**几十秒**降到**亚秒~数秒**。

### 顺带：内存泄漏
`Navi/main.cpp` 约 257 行 `if (!line) { free(line); }` 逻辑反了——`line` 非空时才该释放，
现状是**永不释放**（`getline` 分配的缓冲泄漏）。应改 `if (line) free(line);`。不影响速率但应一并修。

## 2. 🔴 车↔车 HTTP：单线程 + 无压缩 + 整文件

### 证据
`NewWheelCtrl/udp2lcm/udp2lcm.c:55`：
```c
execlp("python", "python", "-m", "http.server", NULL);   // 根目录 /data/test，端口 8000
```
子机侧（见接口文档 §二.3）：
```text
wget http://<主机IP>:8000/defultMap.txt -O /data/test/defultMap.txt
wget http://<主机IP>:8000/roadFile.txt  -O /data/test/roadFile.txt
```

### 问题
- **单线程**：Python `http.server`（`BaseHTTPServer`）一次只服务一个请求；多子机/并发拉图会排队。
- **无压缩**：`Content-Encoding: gzip` 不启用，密排文本地图原样传输。
- **整文件、无条件请求**：每次 `wget` 拉**整张** `defultMap.txt`，即使图没变也全量重传，无 `If-Modified-Since`/`ETag` 协商。
- **无增量**：边建图边更新时，子机要么不更新、要么整图重拉。

### 优化
1. **开 gzip**：换支持压缩的静态服务（或 `ThreadingHTTPServer` + 自定义 handler 加 gzip），文本地图通常压 5~20 倍。
   wget 加 `--header="Accept-Encoding: gzip"` 或服务端预压成 `.gz` 直传。
2. **多线程/并发**：用 `http.server.ThreadingHTTPServer` 或换 `nginx`/`lighttpd`，支持多子机并发拉取。
3. **条件请求/断点续传**：支持 `ETag`/`Last-Modified` + `Range`，图没变就 `304 Not Modified`，不重传。
4. **压缩格式落盘**：地图直接以压缩/二进制格式存盘并提供（见 §3），HTTP 只是搬运压缩块。

## 3. 🟡 地图格式本身：密排 ASCII → 二进制/位压缩/增量

### 现状
地图首行 `range resolution height width`，其后**密排单字符**栅格（`0/1` 等，1 字节/格）。

### 问题
- 1 字节存 1 个 0/1，**信息密度只有 1/8**。
- 占据图**绝大部分是空旷区**，规律性极强，却没做任何压缩。

### 优化（可叠加）
1. **位打包**：占据二值图 1 bit/格 → 体积直接 **÷8**。
2. **游程编码 RLE / 四叉树**：空旷区连片，RLE 往往再压几倍~几十倍；四叉树对大空白区尤其友好。
3. **通用压缩**：gzip/zstd 套在上面，文本图常见 10~50 倍压缩比。
4. **PNG**：把占据图当单通道图像存 PNG，天然无损压缩 + 跨端易解析。
5. **增量瓦片 (tile/delta)**：把图切成固定瓦片，只传**发生变化的瓦片**（建图进行中变化区域很小）→ 实时同步成本骤降。

> 注意：改格式属**协议变更**，需与 App / 上层服务同步（首行 `range resolution height width` 的约定见接口文档 §六.7），
> 按 `CLAUDE.md` 在 `contracts/` 登记。

## 4. 🟡 激光 `laser_t` 编码冗余

### 现状（接口文档 §三.6）
- `ranges` 写**毫米**（整数）；
- `intensities` 实际写**角度**，并非强度；
- `rad0 / radstep` 已是角度制。

### 问题
- 每束激光的角度本可由 `rad0 + i*radstep` 推出，却又在 `intensities` 里**逐束存一遍** → laser 包体积近乎翻倍。
- 高频雷达（一圈数百~上千束、十几 Hz）下，这部分冗余持续占用内部 LCM 带宽。

### 优化
1. **去掉逐束角度**：消费端用 `rad0+radstep` 现算，`intensities` 要么不发、要么发真强度。
2. **ranges 用 `uint16` 毫米**：室内量程足够，省一半。
3. 内部链路若紧张，可对一圈点云做轻量压缩；但优先级低于地图通路。

## 5. 🟡 其它小通路

- **位姿 `POSE`（~15ms）/ `CURRENTPOSE` / 9 字节心跳（500ms）**：包小、频率合理，**无需优化**。
- **`roadFile.txt`**：通常不大，但目前和地图一样走 HTTP 整文件拉取；可顺带享受 §2 的 gzip/条件请求，
  或干脆走 LCM 直发（它本就是机内生成的小文本）。

---

## 6. 优化优先级与预期收益

| 优先级 | 项 | 改动量 | 预期收益 |
|---|---|---|---|
| P0 | MAPFILE 批量打包 + 降 sleep（§1） | 小 | 地图上送 **数十秒 → 数秒** |
| P0 | HTTP 开 gzip + 多线程（§2.1/2.2） | 小~中 | 车间拉图带宽 **↓5~20×**、并发不排队 |
| P1 | 地图位打包/RLE/PNG（§3.1~3.4） | 中（协议变更） | 体积 **↓8~50×**，所有地图通路同时受益 |
| P1 | HTTP 条件请求/增量瓦片（§2.3/§3.5） | 中 | 图未变 0 重传；实时同步成本骤降 |
| P2 | laser_t 去角度冗余（§4） | 小（协议变更） | 内部 laser 带宽 **↓~50%** |
| P2 | 大块地图转 TCP/可靠传输（§1.4） | 中 | 摆脱靠 sleep 防丢包 |

### 一句话结论
**最先做、收益最大的是 §1（删掉 MAPFILE 每行 50ms sleep、改批量+压缩）和 §2（HTTP 开 gzip+多线程）**——
两处都改动小，却能把"建图完到能用图"的等待从几十秒压到几秒。地图格式与 laser 编码的改动涉及协议，
需与 App/上层在 `contracts/` 同步后推进。

> 关联：地图在双车间的**正确性**（而非速率）问题见 `03-双车分布式建图与全覆盖bug分析.md` R3。
