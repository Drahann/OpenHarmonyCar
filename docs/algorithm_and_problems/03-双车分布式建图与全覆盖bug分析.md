# 为什么两辆小车做地图重构与全路径覆盖会出现 bug —— 系统性根因分析

> 本文不只列 bug，而是回答**"为什么双车一起跑就乱、单车却没事"**。把问题归到几条**系统性根因**，
> 每条说清触发链路、现象、为何单车不暴露、改进方向。代码级 bug 见 `02-purplepi-control代码潜在bug.md`，
> 通信瓶颈见 `04-数据传输提速.md`，更优协同分解见 `01-更优全覆盖算法-持续思考.md` 第 5 层。
>
> 依据：`origin/purplepi-control` 源码 + 根目录 `接口功能与对接问题说明.md`。

---

## 根因总览（按影响排序）

| # | 根因 | 一句话 | 主要受害环节 |
|---|---|---|---|
| R1 | **坐标系不统一** | 两车各自里程计原点，地图/路径坐标不在同一参考系 | 建图、覆盖切分、协同避障全部 |
| R2 | **对方车被当静态障碍** | 没有动态障碍过滤，对方进入激光就被烤进地图成"幽灵墙" | 地图重构、覆盖规划 |
| R3 | **共享数据的来源/方向不一致** | roadFile 谁生成谁分发谁消费没有单一事实源 | 覆盖切分、覆盖拼合 |
| R4 | **身份(robotId)运行时才定、默认 0** | 两车可能都当主机，过滤/分工/让行全失效 | 协同避障、覆盖分工 |
| R5 | **协同避障并发模型脆弱** | 单组会话状态 + 小序号，难抗"同时触发" | 相遇让行 |
| R6 | **总线隔离靠默认 ttl，存在埋雷** | 主总线 ttl=0 才隔离，注释里有 ttl=1 一旦启用全串话 | 一切 LCM 通信 |
| R7 | **相向而行的切分策略** | 两车从两端走向中点，必然相遇 | 覆盖执行 |

下面逐条展开。

## R1 坐标系不统一（最核心）

### 链路
- 每台车的位姿来自**轮控里程计 `POSE`**（`NewWheelCtrl/serial`）+ 图匹配修正，原点是**各自建图/定位初始化时的位姿**。
- 地图坐标、覆盖 `roadFile.txt`（每行 `x,y`）、协同避障交换的位姿 `dparams[0..2]`，**都用各自世界系的数值**。
- 双车协同要求把"主机的地图 + 路径"拿给副机用——但副机若不在同一参考系，同一组 `(x,y)` 指向**不同物理点**。

### 现状是怎么勉强维持的
`接口功能与对接问题说明.md` §六.2/§四明确：靠**约定**——"子机从 master 同一物理起点、同一朝向出发"，
并用命令 `0x05` 加载地图时强制初始位姿 `(0,0,0)`。也就是说，正确性**完全依赖人工摆位**：
两车必须物理上摆在同一点、同一朝向开机。

### 为什么会出 bug
- 命令 `0x02 / 'j' / 'l'` 的加载地图用的是**当前心跳位姿**而非强制归零（文档 §六.3 自述），
  一旦走这些路径，副机初始位姿就不是 (0,0,0) → 整张地图与路径**整体偏移/旋转**。
- 真实摆位永远有几 cm / 几度误差，随导航累计 → 覆盖区错位、两车"以为不重叠实则重叠"。
- 协同避障比较两车位姿距离时，如果两车位姿不在同一系，"距离"无意义 → 该让不让 / 不该让乱让。

### 为何单车不暴露
单车只有一个坐标系，自洽即可，从不需要把坐标拿给别人解释。

### 改进方向
- 放弃"同物理起点"假设，改为**统一世界系**：一台车建图并广播，两车各自对该图做**重定位 (relocalization)**，
  得到在**同一地图系**下的位姿与变换 `T_world_robot`。
- 所有跨车数据（地图、roadFile、协同位姿）一律带**坐标系标签**，消费前做显式变换。

## R2 对方车被当作静态障碍（地图重构出 bug 的直接原因）

### 链路
- 占据栅格建图把**任何激光回波**写成障碍（通读 `Navi/map/` 未见 log-odds / hit-miss / 动态过滤）。
- 双车同场：A 的雷达扫到正在移动的 B → B 当前所在格被标为"占据"。B 移动后，旧位置不会及时清除
  （无衰减/无 miss 计数），于是 B 的**整条运动轨迹变成一串幽灵墙**。

### 为什么会出 bug
- **地图被污染**：全覆盖在污染图上规划，把对方走廊当墙绕开 → 出现**永久漏扫带**。
- **触发图匹配跳变**：动态点云让 scan-match 突跳（`NaviInterface.cpp:925` `m_ijumpnum>=6`）→
  误触发 `COOP_AVOID(MATCH_JUMP)`（见 R5/C5）→ 无谓停车。
- **覆盖状态误标**：若把"对方出现处"误并入已覆盖/障碍，覆盖率统计也失真。

### 为何单车不暴露
单车场景里唯一的移动体是自己，激光不会扫到"另一个会动的机器人"，地图里没有幽灵墙。

### 改进方向
- 建图引入 **log-odds + 时间衰减**，让短暂占据能被后续 miss 擦除。
- 更直接：用 `COOP_AVOID` 已知的对方位姿，在建图与覆盖更新时**掩膜 (mask)** 掉对方所在邻域的激光点，
  即"动态障碍不进静态图"（呼应算法文档第 4.2 层"动静分层"原则）。

## R3 共享数据的来源/方向不一致（覆盖切分出 bug 的直接原因）

### 链路（`NaviInterface.cpp` case 2，约 6192–6214）
1. 只有 `robotId==1` 调 `CreateFullPath(...)`，把矩形覆盖路径写到**本地** `/data/test/roadFile.txt`。
2. 随后**两车各自** `ReadFullPathFromFile("/data/test/roadFile.txt")`。
3. 把 `fullPath` 对半切：一台取前半、另一台取后半逆序。

对半切要正确，**前提是两车读到逐字节相同的 `fullPath`**。但：
- roadFile 是 `robotId==1` **本地生成**的；
- 协议里副机靠命令 `124` 从**主机**拉 `roadFile.txt`（方向：主→子，见文档 §二.3）；
- 即"谁生成"和"谁分发"的方向**对不上**——生成方是 id1，分发协议却是主→子。

### 为什么会出 bug
- 另一台车的本地 `roadFile.txt` 可能是**上一轮的旧文件**或**根本没拉到**，于是两车基于**不同路径**切分
  → 覆盖**重叠 + 漏扫**，且各自都"以为自己覆盖了一半"。
- 文档本身对 roadFile 的责任链是矛盾的（§二.3 说子机拉 roadFile，§六.6 说从机生成 roadFile）。

### 改进方向
- 确立**单一事实源**：明确"由哪台车、在什么时刻生成 roadFile，如何原子分发，消费前如何校验一致"。
- 生成后给 roadFile 附**版本号 / 内容哈希**，两车握手确认哈希一致再开始执行，否则重新同步。
- 进一步，放弃"共享一条路径再对半砍"，改为**空间分区**各自规划（见算法文档第 5 层），从根上去掉这个共享点。

## R4 身份运行时才确定、默认 0

### 链路
- `NaviInterface.cpp:326` `robotId = 0;` 默认；真正赋值在 `main.cpp:900` 由 `ROBOT_CONTROL.iparams[0]` 下发。
- 也就是说 robotId 不是开机就定，而是**等一条命令**来设。

### 为什么会出 bug
- 若设置命令丢失/延迟/顺序错乱，两车都停在默认 **0 → 都当主机**：
  - `handleCoopAvoidMessage` 入口 `targetRobotId != robotId` 过滤失效（都 0，谁都收/谁都不收）；
  - 覆盖分工 `if(robotId==1)` 永不成立 → 没人生成 roadFile，或都走同半段；
  - 停机 tie-break"id1 续行、id0 停"在两个 0 之间无意义。

### 改进方向
- robotId 作为**开机强制参数/配置**确定，启动自检 0/1 唯一且互补；未确定前不进入任何协同流程。

## R5 协同避障并发模型脆弱

### 链路（`NaviInterface.cpp` 4753 起 `triggerCoopAvoidance` / 4946 `handleCoopAvoidMessage`）
协同状态机用**单组变量**表达会话：`m_coopState / m_coopActiveSeq / m_coopActivePeer`。同一车却可能**同时**承担：
- 发起方（自己触发的让行会话），和
- 响应方（对方触发的让行会话）。

### 为什么会出 bug
- 两车几乎同时相遇并各自触发时，发起态与响应态**抢同一组状态变量**、互相覆盖；
- 依赖 `robotId==1 续行 / 0 停` 的 tie-break（4992、5018）在状态被覆盖后不一定成立 → **双方都停（死锁等待）**
  或**双方都走（相撞）**；
- `seq` 用 `int8_t`、`>120` 回绕，跨"POSE_RESPONSE→STOP_REQUEST→STOP_ACK"链路在不同角色间传递，
  丢包重传时易**旧 seq 误匹配**。

### 为何单车不暴露
单车没有第二个会话主体，状态机永远只有一个角色。

### 改进方向
- 把"我发起的会话"和"我响应的会话"拆成**两套独立状态**；或用 `(initiatorId, seq)` 为主键的**会话表**。
- 序号扩大范围；超时会话显式作废，避免回绕误配。
- tie-break 规则在两套状态都就绪后再裁决，避免半状态下决策。

## R6 总线隔离依赖默认 ttl，存在埋雷

### 现状
- 主总线 `main.cpp:975` `lcm = lcm_create(NULL)` → 默认 `udpm://239.255.76.67:7667`、**ttl=0**（仅本机）→ 车间天然隔离，**这是对的**。
- 协同总线 `:7668?ttl=1`（显式跨机）→ 两车能通信，**也是对的**。

### 雷在哪
- `main.cpp:978` 有注释行 `// lcm = lcm_create("udpm://239.255.76.67:7667?ttl=1");`。
  一旦被启用，或运维设了 `LCM_DEFAULT_URL` 为 ttl≥1 地址，**主总线 ttl 抬高 → 两车进同一组播组**：
  A 的 `HOKUYO_LIDAR / POSE / CURRENTPOSE / ROBOT_CONTROL / PATH / wheel_ctrl` 被 B 收到并处理 →
  **建图喂错激光、定位被对方位姿污染、轮控被对方 PATH 驱动**，灾难级串话。
- 且主总线**所有信道都不带 robotid 过滤**（只有 COOP_AVOID 过滤），一旦同组就无任何隔离。

### 改进方向
- 删除该误导注释，固化"主总线 ttl=0、协同总线 ttl=1"的约束并写进部署检查。
- 若确需多机共享某些信道，必须给信道名或消息加 robotId 命名空间（如 `POSE_0 / POSE_1`），消费端按本机 id 订阅。

## R7 相向而行的切分策略

### 现状
case 2 把一条路径对半：主取后半逆序、副取前半，两车**从两端走向中点** → 中段必然接近 → 高度依赖 R5 的协同避障。

### 为什么放大其它根因
它把"两车相遇"从偶发变成**结构性必然**，于是 R5（避障并发）被高频压力测试、R2（互相进激光）持续发生。

### 改进方向
- 改**空间分区**：先 BCD 分解，再把 cell 按工作量均衡分配给两车，使其覆盖**空间分离**的区域，
  两车几乎不相遇，协同避障退回"兜底"。详见 `01` 文档第 5 层。

## 一张因果图（文字版）

```
人工同点摆位(脆弱) ─┐
                    ├─▶ R1 坐标系不统一 ─▶ 地图/路径/位姿错位 ─▶ 覆盖错位、避障误判
里程计各自原点 ─────┘
无动态过滤 ─▶ R2 对方成幽灵墙 ─▶ 地图污染 ─▶ 漏扫 + 图匹配跳变 ─▶ R5 误触发停车
roadFile 生成/分发方向不一致 ─▶ R3 两车读不同路径 ─▶ 覆盖重叠+漏扫
robotId 默认0 ─▶ R4 都当主机 ─▶ 过滤/分工/让行失效
相向切分 ─▶ R7 必然中点相遇 ─▶ 高频压测 R5(脆弱并发) ─▶ 死锁或相撞
ttl 埋雷 ─▶ R6 主总线串话(若触发) ─▶ 全面崩
```

## 落地优先级
1. **R4 + R6**：开机定身份、固化总线 ttl —— 改动小、收益大、防灾难。
2. **R1 + R3**：统一坐标系 + roadFile 单一事实源 —— 双车覆盖正确性的地基。
3. **R2**：建图动静分层（掩膜对方）—— 地图重构正确性的地基。
4. **R7 → 空间分区**：从根上减少相遇，顺带卸掉 R5 压力。
5. **R5**：重构协同避障并发模型 —— 作为兜底机制做稳。
