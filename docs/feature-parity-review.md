## 0. 权威依据（A 文档 §四 + §六，逐条核对）

- **紫派 UDP `byte0` → 行为**：`0x00` 首包只建连+发 `7`(init)、**再发 0x00 才进入建图(LCM30, 0.05m)**；
  `0x01` 摇杆(wheel_ctrl)；`0x02` **停轮控+存图(32)+加载图(10)** = 结束建图；`0x03` 目标点(20)；
  `0x04` 取消导航(23)；`0x05` 加载图(10)+位姿归零(0,0,0)；`102/127` 全路径；`103/126` 取消全路径；
  `104/125` **选房间顶点**；`105/124` 子机拉主机图；`106` 加载图+目标；`107/108` 覆盖矩形对角点1/2(→122/123)。
- **🔴 关键事实**：**`Navi` 启动即删除 `defultMap.txt`** → 每次 Navi 运行**必须先建图才有地图**，没有"会话内预存图"。
  所以**不建图 → 无图 → HTTP 拉图永远拉不到 → 导航无图可走 → 全程卡死**。这就是你担心的"明天在建图上卡住"。

## 2. A. 必补回归（影响功能，先施工）

### 🔴 R1 建图 `cmd0` + `cmd2` —— 最高优先，明天测试的硬阻塞
- **为什么硬阻塞**：Navi 启动删图 → 不建图就没有任何地图 → 拉图/导航全废。
- **旧 App**：`Navigationcomponents`(PendingComponent) 有「开始建图」(cmd0)/「结束建图」(cmd2)/「重新建图」。
- **新 App**：`ControlPage` 没有这组（我当初为"进页不误触建图"去掉了 cmd0，连入口一起丢了）。
- **要补**：`ControlPage` 加**建图流程**——地图未就绪时显示建图卡：「开始建图」(cmd0) → 提示用摇杆驱动探索 →
  「结束建图」(cmd2) → 触发拉图 → 地图就绪后转正常操作。建图与 mode 无关（建好图才谈导航/覆盖）。

### 🟠 R2 全路径选房间 `cmd104`
- **紫派**：`104` 选房间顶点(`125`)是 `102` 全路径(`127`)的**前置**（按房间顶点规划）。
- **旧 App**：`distriFullPathPage` 有选房间。
- **新 App**：fullpath 只有开始覆盖/停止，**无选房间** → fullpath 实际跑不全。
- **要补**：fullpath 模式下支持在地图上选房间顶点 → `cmd104`（byte1=vertexId, x,y）。

### 🟡 R3 加载已有图 `cmd5`（次要，单车被建图覆盖）
- 单车每会话都现建图(R1)，故 ControlPage 暂不强依赖 cmd5；**car-agent 已用 cmd5**（子机归零）。
  保留观察：若出现"已有图免重建"需求再给 ControlPage 加「加载地图」。

### 🟢 R4 隐藏/显示摇杆（小 UX）
- 旧可隐藏摇杆腾出地图；新为固定浮层。低优先，可加收起按钮。

## 3. B. 新想法（联合 A 开发；不塞进单车回归）

### 💡 N1 实时建图预览（你提的）
- **现状**：新 App 只在**建完图后** HTTP 拉**整张** `defultMap.txt`。
- **底层已有**：紫派有 LCM `MAPFILE`(地图**分片**) + `SERVICE_COMMAND`(建图/保存**状态**)。
- **想法**：建图时把地图**增量**推到平板，**边建边看地图被构建**。
- **需 A 配合**：把 `MAPFILE`/部分地图经 **UDP 新命令或 HTTP 增量端点**暴露给 App（C/C++ 栈现只 HTTP 整图）。→ 写 `integration-qa` **Q7**。

### 💡 N2 可靠的"地图就绪"信号（取代 App 猜文件 ≥ 3.24MB）
- **现状**：新 App `pollMapUntilReady` 靠"文件 ≥ `MAP_READY_MIN_BYTES`(324e4)"判就绪 —— **脆**（真图更小则永不就绪）。
- **想法**：用紫派 `SERVICE_COMMAND` 的"建图完成/已存图"状态回传给 App 当就绪信号。→ `integration-qa` **Q8**。
  （短期 R1 落地后，可在 `cmd2 结束建图`后**主动拉一次**图，先绕开阈值脆性。）
