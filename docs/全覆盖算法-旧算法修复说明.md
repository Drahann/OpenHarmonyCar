# 全覆盖算法 — 旧算法修复说明

> **背景**：当前 `purplepi-control/Navi/planner/` 下有两套全覆盖（清扫）算法——牛耕法（`algNum=0`）与
> 生成树覆盖 STC（`algNum=1`），由 `Navi/NaviInterface.cpp::CoverageThreadProc` 调度。代码经审查后发现
> 若干会**崩溃 / 未定义行为 / 复杂度爆炸**的硬伤，以及覆盖效率问题。本文逐条列出**需要改动的位置、原因、
> 修复方案**，供成员 A（紫派 owner）在本地施工参考。新算法设计另见
> [`全覆盖算法-新算法设计-BCD牛耕分解.md`](./全覆盖算法-新算法设计-BCD牛耕分解.md)。
>
> 路径均以 main 分支为准：代码在 `purplepi-control/Navi/`。

## 修复优先级总览

| 编号 | 位置 | 问题 | 严重度 | 后果 |
|---|---|---|---|---|
| F1 | `FullPathCoverage.cpp::setValue` | 覆盖标记 21×21 扫描**无边界检查** | 🔴 必修 | 机器人靠近地图边缘时越界访问堆内存 → 段错误/内存破坏 |
| F2 | `ZigzagCoverage.cpp` 四个 detect 函数 | `while(distance<0.25)` 循环内不重算 distance | 🟠 必修 | 步长调小后**死循环**（当前常量下侥幸不触发） |
| F3 | `STCCoverage.cpp::traverseTreeDFS` | 递归 DFS 遍历生成树 | 🟠 必修 | 大地图（粗格数上万）**栈溢出**崩溃 |
| F4 | `NaviInterface.cpp` STC 执行循环 | `goPath.erase(begin())` 每次 O(n) | 🟡 建议 | 整条路径 O(n²)，大地图执行端明显卡顿 |
| F5 | `NaviInterface.cpp` 牛耕换行 | 横向行距(1.0m) < 覆盖全宽(2.1m) | 🟡 建议 | ~50% 重复覆盖，效率打对折 |
| F6 | `NaviInterface.cpp` 多处 | `while(...){;}` 忙等待 | 🟡 建议 | 空转吃满一个 CPU 核 |
| F7 | `FullPathCoverage.cpp::isPointInsideRoom` | 仅支持**凸四边形**房间 | ⚪ 已知局限 | 非凸/非矩形房间识别错误（由新算法解决） |

## F1 🔴 `setValue` 越界访问 —— 必修

**位置**：`purplepi-control/Navi/planner/FullPathCoverage.cpp`，`FullCoverageAlg::setValue`（约 323–344 行）

**问题**：覆盖印记是以当前点为中心的 21×21（±10 格）方块，但循环内**没有任何边界检查**：

```cpp
// 现状（有 bug）
for (int i = -10; i <= 10; i++) {
    for (int j = -10; j <= 10; j++) {
        if (coverageState[(y + j) * GMapWidth + (x + i)] == UNCOVERAGE_BUT_IN_ROOM) {
            coverageState[(y + j) * GMapWidth + (x + i)] = COVERGAED_AND_IN_ROOM;
        }
    }
}
```

当机器人位于**距地图边缘 < 10 格（1m）以内**时，`(y+j)` 或 `(x+i)` 会越界，`(y+j)*GMapWidth+(x+i)`
访问到数组外的堆内存 → 段错误或静默内存破坏。

> 对照：`findNextGoal_Radius / findNextGoal_BFS / ifIPointAroundLegal` 里同样的邻域扫描**都做了**
> `0<=x<W && 0<=y<L` 检查，唯独被每一步反复调用的 `setValue` 漏掉。这是两套算法**共用**的函数，
> 牛耕法和 STC 都会触发。

**修复**：

```cpp
void FullCoverageAlg::setValue(int GMapLength, int GMapWidth, IPoint currentIPoint)
{
    int x = currentIPoint.x;
    int y = currentIPoint.y;
    for (int i = -10; i <= 10; i++) {
        for (int j = -10; j <= 10; j++) {
            int nx = x + i;
            int ny = y + j;
            // 边界检查：超出地图范围直接跳过，避免越界访问
            if (nx < 0 || nx >= GMapWidth || ny < 0 || ny >= GMapLength) continue;
            int idx = ny * GMapWidth + nx;
            if (coverageState[idx] == UNCOVERAGE_BUT_IN_ROOM) {
                coverageState[idx] = COVERGAED_AND_IN_ROOM;
            }
        }
    }
}
```

**验证**：把机器人起点设在贴近地图四角的位置跑一遍全覆盖，修复前必崩，修复后正常。

## F2 🟠 `while(distance<0.25)` 死逻辑 —— 必修

**位置**：`purplepi-control/Navi/planner/ZigzagCoverage.cpp`，
`detectFrontPlan / detectBackPlan / detectLeftPlan / detectRightPlan` **四个函数都有**（约 21–27、75–81、129–135、183–189 行）。

**问题**：以 `detectFrontPlan` 为例：

```cpp
// 现状（有 bug）
Pose tmppose = endpose;
tmppose.x += astarPlanner.GGridSize * 10;
double distance = LinAlg::DistancePose(endpose, tmppose);  // 只算一次
while (distance < 0.25) {
    tmppose.x += astarPlanner.GGridSize * 5;               // 改的是 tmppose
    // distance 从未重新计算！
}
```

`distance` 在循环外计算一次后，循环体内只增加 `tmppose` 却**不重算 distance**。逻辑上：
- 当前常量 `GGridSize=0.1`，`distance = 10*0.1 = 1.0m > 0.25` → 循环不进，**侥幸无害**；
- 一旦有人把前进步长从 10 改小到 < 2.5 格，`distance < 0.25` 成立 → **死循环**（`tmppose.x` 一直加，
  `distance` 永远是旧值）。

属于潜伏 bug，应一并修掉。

**修复**（四个函数同样处理，注意各自的坐标轴 `x±`/`y±`）：

```cpp
double distance = LinAlg::DistancePose(endpose, tmppose);
while (distance < 0.25) {
    tmppose.x += astarPlanner.GGridSize * 5;
    distance = LinAlg::DistancePose(endpose, tmppose);  // 必须重算
}
```

> 提示：这段"太近就加距离"的意图本身可疑——`tmppose` 是在 `endpose` 基础上固定平移 10 格得到的，
> 距离恒为 `10*GGridSize`，根本不会 < 0.25。建议施工时顺便确认这段是否有存在必要，或直接简化为
> 单次平移 + 一个下限保护。

## F3 🟠 STC 递归 DFS 栈溢出 —— 必修

**位置**：`purplepi-control/Navi/planner/STCCoverage.cpp`，`traverseTreeDFS`（约 75–95 行）+
`startDFSTraversal`（约 97–104 行）。

**问题**：`traverseTreeDFS` 是**递归**实现。递归深度 = 生成树最长链长度，最坏 = 自由粗格总数。
粗格数 =（GMapWidth/ROBOTSIZE）×（GMapLength/ROBOTSIZE）。例如原图 700×700、`ROBOTSIZE=7`
→ 100×100 = 1 万个粗格，细长地图下递归深度可达上万层 → **栈溢出崩溃**。

**修复**：改成显式栈的迭代 DFS，产生**完全相同**的带回溯路径（goPath）：

```cpp
// 迭代版，替换 startDFSTraversal 的实现；traverseTreeDFS 可废弃/删除
void STCCoverage::startDFSTraversal() {
    goPath.clear();
    if (path.empty()) return;

    std::unordered_map<IPoint, bool, PointHash, PointEqual> visited;
    // 栈帧：当前节点 + 下一个待检查的邻居下标
    std::vector<std::pair<IPoint, size_t>> stk;

    IPoint root = path[0];
    visited[root] = true;
    goPath.push_back(root);          // 进入根
    stk.push_back({root, 0});

    while (!stk.empty()) {
        IPoint node = stk.back().first;
        size_t& idx = stk.back().second;

        // 找下一个未访问的子节点
        bool descended = false;
        auto& nbrs = adjList[node];
        while (idx < nbrs.size()) {
            IPoint nb = nbrs[idx++];
            if (!visited[nb]) {
                visited[nb] = true;
                goPath.push_back(nb);        // 前进：进入子节点
                stk.push_back({nb, 0});
                descended = true;
                break;
            }
        }

        if (!descended) {
            stk.pop_back();                  // 当前节点所有子节点处理完
            if (!stk.empty()) {
                goPath.push_back(stk.back().first);  // 回溯：父节点再入路径
            }
        }
    }
}
```

**等价性说明**：原递归是「进入即压入当前点；每个子树返回后再压一次当前点」。迭代版「找到子节点就压子节点并下钻；
某节点无更多子节点则出栈、回到父节点并压父节点」，输出序列逐点一致。`goPath` 不变，下游执行逻辑无需改动。

> 注：`traverseTreeDFS` 改为迭代后不再被调用，可从 `.h` / `.cpp` 中删除以免误用；若担心影响编译可暂留空壳。

## F4 🟡 STC 执行循环 `erase(begin())` O(n²) —— 建议

**位置**：`purplepi-control/Navi/NaviInterface.cpp`，STC 分支执行循环（约 6135–6152 行）。

**问题**：

```cpp
while (!pObject->fullCoverageAlg.stcCoverage.goPath.empty()) {
    ...
    IPoint nextIPoint = pObject->fullCoverageAlg.stcCoverage.goPath.front();
    pObject->fullCoverageAlg.stcCoverage.goPath.erase(
        pObject->fullCoverageAlg.stcCoverage.goPath.begin());   // 每次删头 O(n)
    ...
}
```

`std::vector::erase(begin())` 需要把后面所有元素整体前移，单次 O(n)，整条路径走完 O(n²)。
goPath 含回溯点约 2n 个，大地图下执行端明显卡顿。

**修复（二选一）**：

- **方案 A（最小改动）**：用下标推进，不删元素：

```cpp
size_t gi = 0;
while (gi < pObject->fullCoverageAlg.stcCoverage.goPath.size()) {
    ...
    IPoint nextIPoint = pObject->fullCoverageAlg.stcCoverage.goPath[gi++];
    ...
}
```

- **方案 B**：把 `goPath` 类型从 `std::vector<IPoint>` 改为 `std::deque<IPoint>`，再用 `pop_front()`（O(1)）。
  需同步改 `STCCoverage.h` 中 `goPath` 声明及所有遍历处。

推荐方案 A，影响面最小。

## F5 🟡 牛耕法行距过密导致 ~50% 重复覆盖 —— 建议

**位置**：`purplepi-control/Navi/NaviInterface.cpp` 牛耕分支换行逻辑（撞障碍后调用 `detectRightPlan` 横移），
横移量来自 `ZigzagCoverage.cpp::detectRightPlan` 的 `tmppose.y -= GGridSize * 10`。

**问题**：覆盖印记半宽 = 10 格 = 1.0m（`setValue` 的 ±10），即单条扫描线覆盖**全宽 2.1m**；
但换行横移只 **1.0m**。相邻两行覆盖区重叠约 1.0m ≈ **50% overlap**，实际清扫面积约为有效面积的 2 倍。

**修复**：把换行横移量调整到接近**覆盖全宽**（约 20 格 = 2.0m），与 `setValue` 的印记尺寸匹配：

- 将牛耕换行使用的横移常量从 `GGridSize * 10` 调到 `GGridSize * 20`（仅改"换行"那一次横移，
  沿行前进的 `detectFrontPlan` 步长保持 10 不变——那是行内行进分辨率，不是行距）。
- 更稳妥的做法：把**覆盖半宽**和**换行行距**抽成同一个具名常量（如 `COVER_HALF = 10`、
  `ROW_STRIDE = 2*COVER_HALF`），两处共用，避免再次不一致。

> ⚠️ 这是行为调参，必须真机/仿真验证：行距过大会反向变成**漏扫**。建议从 18 格起试，结合 `setValue`
> 实际印记和机器人物理清扫宽度标定。

## F6 🟡 忙等待空转 —— 建议

**位置**：`purplepi-control/Navi/NaviInterface.cpp`，如 `while(pObject->fullCoverageAlg.algNum == -1){;}`、
`while(pObject->m_waypoints.size() > 0){;}` 等。

**问题**：空循环忙等待会吃满一个 CPU 核。代码里其实保留着 `pthread_cond_wait` 的注释——本就打算用条件变量。

**修复**：改用条件变量 / 信号量等待，或至少在循环体里加 `usleep(几十 ms)` 让出 CPU。属低优先，
不影响功能正确性，可在性能优化阶段统一处理。

## F7 ⚪ 房间边界仅支持凸四边形 —— 已知局限

**位置**：`FullPathCoverage.cpp::isPointInsideRoom`（叉积法）+ `manualGetRoomBoundary`（固定读 4 个顶点）+
`autoGetRoomBoundary`（凸包，注释自述"未调试"）。

**问题**：`isPointInsideRoom` 用「点在每条边同侧」判定，要求多边形**凸**且顶点按固定顺序（左下→右下→右上→左上）
录入，本质只支持**凸四边形 ≈ 矩形**房间。真实房间多为非凸（L 形、带隔断），会误判房间内外。

**结论**：这不是简单 bug，而是方法局限。**由新算法解决**——BCD 牛耕分解直接在栅格占据图上工作，
不需要"房间是凸多边形"的假设，天然支持任意形状、带障碍的房间。详见
[`全覆盖算法-新算法设计-BCD牛耕分解.md`](./全覆盖算法-新算法设计-BCD牛耕分解.md)。
